# 设计前上下文：先读已有设计，再生成

在两道文档问答与需求提炼之后、设计方向访谈及任何页面生成之前执行。所有宿主使用同一[原生问答](interactive-input.md)。本阶段只读取云端设计，不创建项目/文件/画板，也不上传内容。

## 1. 先确定新建还是补充

只问缺失项。用户已说“补充已有设计”“修改原画板”或已明确给出目标时直接复用，不重新问一遍：

| 问答 | 输入/选项 | 后续 |
|---|---|---|
| 本次属于哪种设计？ | 全新设计；补充已有设计；修改已有画板 | 决定是否必须读已有设计 |
| 【已有设计链接｜必填】 | 真实文件、页面、画板或项目链接，可自由输入 | 补充/修改时必须取得并验证；新建设计不索取此链接 |
| 项目中参照哪份设计？ | 实际可读文件/画板/组件库候选，或用户提供的基准链接 | 只有 Project 链接不能证明有统一样式，不任取第一个文件 |

文件/页面/画板链接通常已足够定位基准，只在多个风格或版本会影响结果时再问。Project 作为最终落点时，另选的样式文件仅作为基准；保留两个不同身份，不能把追加落点悄悄换成基准文件。

用户给的已有链接也可能仅作新设计的参考。按其真实用途记录，不能把“参考这个文件”推断为授权修改这个文件。

## 2. 生成前读回真实约束

- 需要认证时，在本阶段按[连接与浏览器授权](cloud-handoff.md#连接与浏览器授权)读取对应平台说明、启动宿主 OAuth 并验证。不能为了坚持“上传时才授权”而跳过现有设计分析。
- 对 Ardot，优先通过官方云端 MCP 读取真实文件/节点链接；不要求本机客户端。明确使用本地 MCP 时才打开目标文件并核对活动文件身份。不创建新文件来解决已有目标的读取问题。
- 读回平台、团队/账号、Project/fileId/pageId/nodeId、目标名称和必要权限；确认链接对应真实的设计文件/节点，区分目标落点与样式基准。
- 先读取用户已提供或当前项目已绑定的正式设计文档、tokens 或云端“设计规范”区域，按[项目规范约定](project-style-contract.md)核对稳定 projectId、specVersion、适用范围、组件和局部例外。没有文档时从相关设计提取并补建规范；有文档不能跳过实际设计核对。不要自动把站点不同模块当成新品牌。
- 获取本次相关的字体/字号、颜色、间距、圆角、布局密度、画布/响应式尺寸、组件及变量/样式引用。优先选目标附近的代表性页面；不为分析样式读取全部无关文件。
- 核对需求与已有规范：功能/页面范围、文案结构、已有组件适配、平台限制和已知写入路由。写权限及能力能只读确认时提前检查，不以创建试验节点来探测权限；不确定就说明具体缺口。

链接缺失、无法读取、身份不明、样式基准不明或关键冲突未解决时，保持上下文待答，不能直接按默认风格生成正式页面。先解决连接或输入问题。用户明确改为“先做本地草稿”时可继续，但记录尚未验证的约束及可能返工，不把草稿当已满足既有项目规范；没有这个授权时不能把失败默默变成忽略已有设计。

## 3. 风格冲突在生成前问清

规范文档与实际设计值冲突时，展示具体维度、两方版本/来源和受影响模块，只问需要的取舍；不按文件名或更新时间自动选“最新”。项目规范、远端设计、用户新要求和普通参考各自记录；用户只提供规范而未给已有设计链接时，先读规范继续独立整理，正式追加/修改仍须取得真实目标。

展示已有样式与需求中明确要求的实际差异，例如“现有正文 14px、圆角 4px；需求要求 16px、圆角 12px”。有实质冲突时，通过原生问答选择“沿用已有规范”“按本次新要求”“自定义调整”，说明影响范围。用户已明确授权以其中一方为准时直接采用，只补问未决维度。

此时提供的是差异和必要的小样，不先生成整套页面再让用户选择重做。无冲突时从已有规范及设计继承方向，在参考后的全局基础阶段只问仍缺少的信息；不要重新询问已经读出的字体、颜色和圆角来推翻基准。

## 4. 固定本次设计基准

进入方向/生成前，记录：

- designMode：new / append / update。
- target：实际交付目标 URL、实体类型及稳定 ID；参考用途的链接另记。
- styleReference：实际读取的基准文件/页面/组件与样式来源。
- baseline：读取时间、可取得的远端 revision/更新时间；拿不到版本号时记录相关属性摘要、节点 ID 和必要截图，不编造 revision。
- styleSpec：本次采用的规范来源/链接、稳定 projectId、specVersion/baseVersion、适用模块、局部例外和缺项；规范身份与平台 projectId 不混用。
- decisions：已解决冲突、用户取舍、继承规则和仍允许推荐的缺项。
- readiness：新建为 not_applicable；补充/修改须 context_ready，或用户明确授权的 draft_only。

上下文 ready 后才进入设计方向与正式页面生成；既有规范成为生成输入，而非上传时才加上的检查条件。首次样式冲突处理属于本阶段。

## 5. 上传时仅复核与恢复

平台选择和上传阶段复用已绑定目标、样式基准及已回答选项，不重新收集链接或重新访谈风格。用只读方式复核目标身份、访问权限、相关 revision/基线摘要，然后执行原定追加/更新。

只有用户中途改目标/改需求、远端相关样式或组件发生实质变化，或出现此前未能确认的平台限制时，才说明变化、重新问受影响部分并调整局部设计。无关节点变更不使全部设计失效，也不能重新问整套问题。用户到上传阶段才首次提出“改为补充已有设计”属于范围变更：回到本阶段，说明新增约束可能导致局部返工，不把它当作正常的默认顺序。

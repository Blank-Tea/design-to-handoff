# 项目设计规范：保存、交付与同站复用

规范是同一网站后续设计的稳定输入，不能只保留本轮聊天答案。本约定与[会话记录](session-contract.md)区分：session 记录过程；design-spec.md 与 tokens.json 记录项目设计决定，可跨聊天与模块复用。

## 同一来源，两个表达

- **design-spec.md**：正式设计文档，包含需求/页面说明，以及可独立复用的“全局设计基础”章节。人读规则、来源、组件用法、例外和版本。
- **tokens.json**：与同版本文档一致的机器可读值；用于生成页面和建立平台变量/样式。不能只给色板图片或无来源的 CSS。
- **云端“设计规范”页/区域**：上传设计时，在同一已授权设计文件中创建或追加可编辑文字、色板和组件说明。完整全局规则、token 值/别名表及版本需可读回；只有本地路径、外链或摘要不足以支持无本地副本时的复用。页数受限用既有页空白区域。不得覆盖其他规范版本或修改全局共享样式。

三种表达来自同一份已解析的规范；发生改动同步更新。未选择本地副本时，Markdown/JSON 可在临时目录生成用于构建和检查，但不擅自持久保存。上传授权范围包含本次设计及其规范说明，须在上传选择前说明；不额外发布到无关云文档或公开网站。

## 正式文档必须包含

1. **项目身份与版本**：稳定 projectId（本地逻辑 ID，与平台 projectId 分开）、名称、产品/站点范围、specVersion、日期、draft/confirmed 状态、baseVersion、适用模块与终端。新项目从 1.0.0 开始；草稿不冒充已确认版本。
2. **需求和页面**：来源、目标人群、REQ→viewId、布局/文案/交互/权限/状态与响应式、覆盖和未决项，沿用[正式文档结构](session-contract.md)。
3. **全局设计基础决策表**：覆盖目录各维度的具体值/行为、范围、来源类型及来源定位、确认状态；不适用项有理由。来源用 user / existing_spec / existing_design / recommendation / reference；推荐经用户授权仍保留 recommendation，另记授权事件，不能改成“用户指定”。
4. **Token 与组件约定**：语义命名、值和单位、模式、别名关系、字体替代、字号行高、栅格断点、密度间距、圆角层次、组件/导航/状态/动效、可访问性和内容；组件引用及平台样式/变量 ID 仅填真实已取得的值。非数字规则也需保存。
5. **参考采纳说明**：URL/截图及证据范围；分别记录布局/交互/视觉采纳；没有授权沿用的品牌资产和仅估计的值不能进入已确认基础而不注明。
6. **局部例外**：只对哪个模块/viewId、原因、覆盖哪个 token/规则、基础版本；未列例外继承全局。新增模块不能静默改变全站按钮、字体或主色。
7. **变更记录与复用入口**：版本/日期、变更的 token/规则、原因和影响范围、兼容/迁移说明；设计文件/规范区域/代表画板的真实链接与稳定 ID，远端读回时间和验证状态。

## Token 格式约定

使用本技能的轻量 JSON 格式，**不是对符合 DTCG 或任一平台导入规范的承诺**。生成或导入平台变量时做实际类型映射。以下只是最小结构示例；正式 tokens 必须补齐全部适用维度的可参数化值，行为规则写在同版本设计文档中：

```json
{
  "schemaVersion": "1.0",
  "projectId": "example-service-site",
  "specVersion": "1.0.0",
  "defaultMode": "light",
  "modes": ["light"],
  "tokens": {
    "color.brand.primary": {
      "type": "color",
      "values": {"light": "#2563EB"},
      "source": {"kind": "recommendation", "ref": "F02", "basis": "无既有品牌的服务网站"},
      "status": "confirmed",
      "scope": "global"
    },
    "button.primary.background": {
      "type": "color",
      "alias": "color.brand.primary",
      "source": {"kind": "recommendation", "ref": "F13"},
      "status": "confirmed",
      "scope": "global"
    },
    "radius.control": {
      "type": "dimension", "value": 8, "unit": "px",
      "source": {"kind": "user", "ref": "F09"},
      "status": "confirmed", "scope": "global"
    }
  },
  "overrides": [],
  "platformMappings": []
}
```

每个 token 有稳定名称、type、值/单位或 alias、来源与 scope。mode 无关值用 value；随主题变化用 values，每个已支持 mode 有值；alias 不再重复写 value/values。所有 alias 可解析且无环，模式/组件引用不能悬空；不能把 `8px`、数值 `8` 和工具单位混用。status 用 confirmed/proposed/pending；confirmed 可来自已回答项、明确授权推荐或已核对继承，不等于已远端验证。

规则：基础原值 → 语义 token → 组件 token，优先引用稳定语义名；不为每个页面重新创造同义颜色。局部覆盖放 overrides，记录 module/viewId、baseVersion、token、value/alias 和原因。platformMappings 在实际写入后才增加平台、文件/节点/变量/样式 ID 及映射结果，不伪造可用组件或 ID。JSON 中不存密钥或凭证链接。

## 生成前与上传后的两次落档

**生成前**：基础问答收束后把全部决定写入文档和 tokens；生成页面只从这套值取用。检查各适用维度是否已决定或标明待验证，字号/状态/模式一致、别名可解析。draft_only 继续保持草稿。

**上传后**：在同一目标中持久化规范区域，读回文字、代表性色值/排版/圆角/组件及实际映射。检查规范值、源设计值与远端实际值一致；转换造成字体/样式替换时先修复，无法修复的差异明确记录为降级/待验收，不以读回值自动覆盖已确认全局规范。同步补上文件/规范区域/viewId 的真实链接、已应用 specVersion、验证结果和变更记录；选择本地保存时也回写本地文档与 tokens。

云端页/区域记录自身稳定 ID 与最后读回时间；远端 revision 在最后一次写入后记录到本地交付记录/会话，不为把 revision 写回云端反复制造新 revision。断点恢复复用记录的规范节点 ID，不重复创建多份“最新版”。设计图成功而规范未保存/无法读回时，分别报告“设计已上传；规范持久化待完成”，保留恢复入口，不能称全流程完成。

未选本地保存且暂不上传时：在聊天交付完整可复制设计规范和 token 数据，明确尚无可自动读取的持久规范入口，后续需要用户提供这份文档；不声称聊天记忆能跨会话自动继承。已有临时产物按主入口的保存/清理约定处理，不能在唯一可恢复来源未交付时删除。无本地副本但已上传时，以云端规范区域为持久入口；下次读回该区域而非猜测上次聊天。

## 同站后续模块怎么复用

1. 在[前置上下文](design-context.md)先读取用户提供/项目已绑定的 design-spec、tokens 或云端规范区域，核对 projectId、版本、适用范围和关联设计；不全盘搜索用户设备，不依赖跨聊天记忆。
2. 读取本次相关的远端代表性设计/组件，与规范对照；文件名较新不等于已采纳版本。文档与实际不一致、多个版本/站点身份不明时展示具体差异，只问需要的取舍。无链接/无法读回按前置上下文阻塞或用户授权 draft_only，不能用默认风格顶替。
3. 固定 baseVersion，只补本次缺项。沿用主题、字体、间距、组件和状态；参考站仅影响已允许变化的排版/交互。完成新模块后把适用模块与新链接补入同一版本记录，不为新增页面自动重建全站规范。
4. 新增兼容 token/组件规则可升 minor，说明性修正可升 patch；改变已有全局视觉/行为合同用 major 并先说明受影响模块。仅新增页面且未改规则时无需升规范版本。项目已有版本习惯时沿用并记录。
5. 用户只想某模块不同：作为局部例外，不修改全局。用户要全站改风格：先形成具体差异与影响范围，已有授权范围内更新规范；旧模块是否迁移须按用户范围执行，未迁移的模块标出仍采用的版本。不要把一次追加设计当作全站改造授权。

完成后返回“下次继续设计请提供”的规范文档/云端区域链接、projectId 和 specVersion，以及本次模块的继承与例外摘要。
